## Bypass summary

Every enforcement layer I re-executed has at least one escape the agent fully controls, and I confirmed each by direct execution in a faithful bind-mount namespace (no LLM sessions).

1. Command-text classification, not execution. The deterministic git/bash guards parse the command STRING. `bash -c "git commit"`, `eval "git commit"`, `bash -c "git push origin master"` all run while all 20 PreToolUse hooks exit 0; only the naked forms (git commit, git push --force) are blocked. The authors admit this (git_command_classifier.py:443, block-branch-pr-worktree.py:44). Same bypass applies to subagents. Config-guard is worse: it catches the Edit tool and echo> redirects but allows sed -i, perl -i, python open().write and chmod -x on the hook files themselves.

2. Forgeable trust roots. All authority state lives in agent-writable files (harness_state_dir()='/tmp', or the product repo) and is validated by shape/freshness, never provenance. I confirmed: forging the /do consent flag ('echo true > ...') re-enables unlimited Edits AND flips git commit to allowed; self-minting a /tmp/claude-grants/<sid>.json flips git commit to allowed; setting overnight-state status=cancelled releases the time-lock; a close-report hand-written by Bash passes close-verdict ('yes') and the existence-only commit mint; the push-gate token is accepted for any ancestor of HEAD from any session. The repo's own fixtures already label grant-self-minting a 'MEASURED CORRECTION'.

3. Self-declared identity. Role-based write policy and the subagent-stop gates resolve role from payload['subagent_type']/agent_id (the sentinel the subagent chooses to Read), ignoring payload['agent_type']. Under the claimed CLI 2.1.295 shape (agent_type only) a QA edits source (tool-policy rc=0); an unregistered QA stops with no report (e2e rc=0). The e2e gate only bites a QA that voluntarily self-registered.

4. Advisory-by-default and narrow signatures. CLAUDE_OBLIGATION_GATE/STOPGATE/BARRIER/TERMINAL and CP_ENFORCE_MODE appear zero times in settings.json or settings.template.json; all default advisory. A valid obligation block even short-circuits the one default-on schema check (exit 0 at artifact-contract :1123). The completion gate blocks only the exact sole-missing-completion signature, so QA-FAIL, abandonment and no-artifacts Stops all pass.

5. Gates that error or hide their reason. stop-completion-gate loads the resolver from project_dir/scripts and dies with FileNotFoundError in every product repo (blocks every legitimate /dev Stop). The Stop coordinator exits 2 with zero stderr bytes, replacing each phase's reason with sha256, so even a correctly-blocking gate tells the agent nothing. /dev-overnight deadlocks at Step 2 (empty required_calls + HARD CUTOVER, no republisher) and can never end (closeout fields have no producer).

One caveat I could not execute: Claude Code's core permissions.deny engine. Live settings.json does carry Edit(.claude/settings.json), Edit(.claude/hooks/**), Edit(.claude/scripts/**), Edit(.claude/CLAUDE.md) in deny, but as relative globs; whether they match an absolute /root/.claude target from a product-repo cwd is a CLI-engine question I cannot run here. The hook layer provides no such coverage, and the Bash sed/python write vectors bypass tool-glob denies regardless.

## Can the harness force compliance?

No. Today the harness cannot force a rogue, interrupted, or adversarial agent to comply. It is, by its authors' own words, 'an AGENT SPEED-BUMP, not an adversarial sandbox.'

What actually blocks (deterministic, re-executed): the naked git-privilege guard (commit/push), bash-safety (rm -rf, push --force, removal policy), the TodoWrite order gate, a registered QA stopping with no qa-report (e2e-enforce rc=2), and the commit grant's single-use binding. These are real. But each is defeated by a vector the agent controls:
- bash -c / eval / python-subprocess indirection runs the forbidden git/bash op past the string classifier;
- forging an agent-writable trust file (consent flag, sentinel grant, overnight status, close-report, push token) grants the privileged action;
- skipping the voluntary sentinel Read leaves role enforcement inert;
- the strongest stop/subagent gates are advisory and unset in settings;
- the completion gate errors out in product repos, and the coordinator hides every reason.

For an INTERRUPTED agent specifically: /restart recovery evidence is forgeable (Bash-edit the restart-state file -> finalize reports complete for never-resumed agents; any reply counts as recovery), and a killed /do session leaves stale consent/sidecar/registry that SessionStart(resume) never surfaces. So 'resume the same agent' (Production Lesson 16) is not mechanically guaranteed.

To make compliance mechanically true you would need, in rough order of leverage:
1. Enforce at the execution boundary, not the command text: a wrapper `git` earlier on PATH, or mandatory per-repo git hooks via a pinned core.hooksPath, so bash -c / eval / python / aliases / base64|bash are all caught. This single change closes the largest class of bypasses.
2. Make trust artifacts unforgeable: mint a per-session secret in an env var never exposed to the Bash tool, write every consent flag / grant / token / overnight-status / close-verdict as an HMAC-signed blob, and have every consumer verify the signature. Add a PreToolUse write-target deny (covering Bash write verbs AND Write/Edit) over the trust-artifact namespaces so the agent cannot create or overwrite them.
3. Resolve role from the runtime payload's agent_type (which the CLI sends and the model cannot forge), fail closed when role is unknown for producer roles, and refuse a check-in whose sentinel role disagrees with agent_type.
4. Turn the obligation/CP gates to block in settings.json env, stop the advisory obligation branch short-circuiting the legacy schema block, and make the completion gate block on ANY resolver status=fail (not just sole-missing-completion), loading the resolver from the harness home.
5. Fix the reason channel: the coordinator must relay the failing phase's stderr on exit 2.

Until (1) and (2) exist, every other gate rests on files and command-strings the adversary owns, so the honest answer to the user's third question is: it can slow a cooperative agent, but it cannot compel a hostile or broken one.
