### Part B: the landing re-syncs a home (tracked code)

Land everything inside P7b's landing (its trigger in hooks/auto-commit.sh, before the git-repository check, f8c18c2
:21; its fast path and its work, at the time of writing `scripts/install/land` and the `render-settings land`
subcommand with the log `logs/landing.log`; take the real names from P7b's PR). P10 and possibly P9 added steps there;
keep theirs intact.

**B1 Detection, cheap.** One constant: the old root id(s) from A4 (at the time of writing
e34918cf6760fe83104473a0285bb44ee3dea59e; confirm against `--all` on the mirror). The home needs a re-sync exactly
when the old root object exists locally and the current branch's upstream remote-tracking ref exists and does not
reach it (the human's pull fetched the rewritten history). On a pre-rewrite home before the publish, the upstream
still reaches the old root: do nothing. On a re-synced home still in B7's grace both checks stay true, so the
landing must find "nothing left to re-sync" from git's own data (for example `git for-each-ref --contains <old root>`,
about 16 ms over 844 commits here, plus the reflog check) within acceptance 9(c)'s grace bound. On a home after the
prune, or a clone made after the publish, the object is absent: one `git cat-file -e`, nothing else. Measure every
path (acceptance 9).

**B2 Order with P7b, and when to wait.** Run the re-sync only when P7b's landing has nothing left to do on the home,
never while P7b would still land it (its "upgraded" state at the time of writing): P7b detects the pre-pull revision
from the HEAD reflog that B7 clears, so P7b lands first, at the same or the next Stop. Wait,
changing nothing and saying why in the notice, while a rebase, merge, cherry-pick, revert or bisect is in progress in
the home, while `index.lock` exists, while HEAD is detached, or while P7b's lock is taken. A stopped rebase onto the
rewritten history (a local commit that conflicts with upstream) is P7b's S4: report the operation and the number of
conflicted paths, never abort, continue or reset anything. One kind of stopped rebase is not the owner's work: a
rebase replaying pre-rewrite public commits (commits that have counterparts, B4), which a pull starts when it cannot
find the fork point (acceptance 5b). Decide by that experiment whether the landing aborts exactly this kind: rule:
abort it only if the abort restores the pre-pull HEAD, index and files byte for byte and keeps pull.sh's stash entry,
and the following B3 move and the next /pull end with `assert-resynced.sh` passing; otherwise report it like S4.
The same pull can also complete, and then the branch carries copies of pre-rewrite public commits (same author,
author date and message as an old public commit) that a later /push would publish. Reproduced during planning: a
replayed copy re-added a literal that the rewrite had replaced and a later replayed copy removed it again, so the tree
was right and the history was not. Treat such a branch as B3 treats a refused merge pull: its local-only commits are
the commits above its upstream that are not such copies; when the newest copy's tree equals the upstream tip's tree
(the copies net to nothing), re-create the local-only commits on the upstream tip and move the branch with a
compare-and-swap, working tree and index untouched; otherwise leave the branch and name the copies in the notice.

**B3 The move changes refs only.** The re-sync never writes the working tree or the index (P7b's own S3 repair keeps
its rules; B2's abort, if its experiment allows it, only restores the pre-pull state). Every local ref that reaches
the old history is re-expressed in the rewritten history with the same content, under two invariants that the tests
check for every re-created commit: its content is kept (its tree when it is re-parented, its own change when it is
replayed), and, when its new parent is a commit of the rewritten history, its diff against that parent adds no listed
literal that its diff against its old parent did not add (no rewrite replacement is undone). A parentless re-created
commit keeps its old tree as local content and is checked for the first invariant only. The only content ever left
out is B5's credential-file class.
- **The current branch.** After a rebase pull it is already on the rewritten history (fact 4). After a refused merge
  pull, or when only a fetch happened, its local-only commits are the commits reachable from it that have no
  counterpart in the rewritten history (B4), and its fork point is the newest commit below them that has one (the
  remote-tracking reflog cannot be relied on, fact 4). When the fork point's tree equals its counterpart's tree
  (expected whenever the fork point is a master that contains this phase's merge: no literal is left in those trees,
  A7 "HEAD tree unchanged"), re-create the local-only commits on top of the counterpart with `git commit-tree`, each
  with its own tree and message, and move the branch with a compare-and-swap `update-ref`: HEAD's tree, the index and
  every file stay byte-identical, and the home is behind origin by what upstream merged since its last pull, which the
  next /pull brings normally. When the trees differ (not expected: a home that runs this code has pulled a master
  whose tree holds no literal), re-parenting would carry old literals into the new history as a change: do not move
  the branch, re-sync the other refs, and say in the notice that the next /pull completes the move (its rebase replays
  the local-only commits by their changes).
- **Other local branches.** Not checked out, so their commits can be replayed by their changes onto the fork point's
  counterpart without touching the working tree (for example `git merge-tree --write-tree --merge-base`, which git
  2.43 has; check that the home's git supports what you use and fall back when it does not); re-parent with
  `git commit-tree` when the trees are equal. A branch whose replay conflicts, or with no matched commit at all, keeps
  its content as one parentless commit holding its tip tree, counted in the notice (D10, with the test of the
  invariants).
- **Local-only commits' identity.** Kept as they are when their author and committer are not on the home's
  private-literal list; otherwise mapped to the identity the rewritten upstream's own non-merge commits use (read
  from the rewritten history, never hard-coded: the GitHub handle may appear only in URLs and the copyright line).
  Count them in the log. Fact 1 says the owner's own commits already use a public identity, so expect 0.

**B4 Counterparts, decided by experiment.** Find the rewritten counterpart of an old public commit without data
from the rewrite on the home: for example by (author date, committer date, tree), falling back to (author date,
committer date) when unique. Experiment on the real dry run: run your matcher over every old commit reachable from
the pre-rewrite refs and compare with filter-repo's commit-map. Rule: precision 100% and every fork point a home can
have (every old master tip and every phase merge) matched -> use the matcher; otherwise the publish adds one commit on
top of the rewritten master holding the old -> new map as a tracked file (A8 step 5 then pushes it) and the landing
reads it from the upstream tip; record which and why (counts in the PR).

**B5 Checkpoint refs keep their content.** For every `refs/checkpoints/*`: the snapshots along its first-parent chain
(down to the first commit that is not a checkpoint commit) are re-created with the same trees and messages in the same
order, the oldest re-created one becoming a root (or a child of its base's counterpart; D10), and the ref moved with a
compare-and-swap while holding `<git dir>/checkpoint-core.lock` (fact 8), so a concurrent `write_checkpoint` neither
loses a snapshot nor writes onto the old chain. A long chain may be re-created in bounded slices across Stops or by a
detached worker that holds the landing lock (D10, measured: acceptance 10). A re-created snapshot leaves out the paths
of the checkpoint producer's own PII file class (checkpoint-core.sh `CHECKPOINT_PII_BASENAME_PREFIXES` and
`CHECKPOINT_PII_PATH_COMPONENTS` :87-88, which `write_checkpoint` drops from every new snapshot, :553-587): snapshots
taken before that rule can hold `.claude.json`, and PLAN-v2's goal "no local ref keeps that file" (:853) holds only if
the re-created chain drops it. Build such a tree with a temporary index, never reading the blob, and count the
dropped paths in the notice.

**B6 Stash, backups, remote-tracking refs, other refs.**
- Stash: every entry, in order, re-created with the same work-tree, index and untracked trees and message on a base
  that is the counterpart of its base commit when B4 finds one with an identical tree, else a parentless commit with
  that tree; the list keeps its order and count; crash-safe (a re-sync killed between any two steps loses no entry and
  completes at the next Stop). Never `git reflog expire --all` (fact 5).
- `refs/backups/*` (fact 8): a ref whose commit has a counterpart (B4), or whose tree exists in the rewritten history,
  is deleted (its content, with the rewrite's replacements, is there); any other (no counterpart: a commit that was
  never on a public branch) is re-created as a parentless commit with its tree and message under the same name. A
  tree-only rule is not enough: a pre-P0 home holds a backup ref for every commit it made (fact 8), and most of those
  trees held literals before P8, so they have no identical tree in the rewritten history and would be kept with their
  old content.
- `refs/remotes/*` that reach the old history (stale branches, `origin/checkpoints/*`): deleted; the next fetch
  recreates what still exists.
- Anything else that reaches the old history (`refs/original/*`, `refs/notes/*`, `refs/replace/*`, ORIG_HEAD,
  FETCH_HEAD, any other ref): the same rule as backups for refs, deleted for the pseudo-refs. Never touch a ref that
  does not reach the old history.

**B7 Reflogs and objects.** Remove the reflog entries that reach the old history through either of their two values
(git's reachability reads the old and the new value of every entry, fact 4), per ref, in every log under the git
directory's `logs/` including symref logs such as `refs/remotes/origin/HEAD`; refs/stash excluded; an entry whose two
values both lie outside the old history is kept. Then prune the pre-rewrite objects with a grace that is safe with
concurrent writers (sessions, checkpoints, an agent's `git add`): never `--prune=now` on a live home (fact 6). Run the
prune at most once per grace period, keyed to git's own artifacts (for example the age of the newest pack), never to a
new state file; until then the fast path pays B1's two checks. Decision by experiment (acceptance 10): the grace and
the method under which a concurrent checkpoint write and a concurrent `git add` + commit both survive with `git fsck`
clean. Other landing steps read the HEAD reflog that this step clears: P7b's "upgraded home" test (P7b R1: only such
a home is landed, and a landed home's installed git hooks are refreshed) and P10's per-home need test for retired hook
files (P10 R-c: a reflog revision whose settings register the file, and the reflog's timestamps). Their verdicts must
be the same after the re-sync as before it (acceptance 3). Rule: if removing the entries changes a verdict, re-express
the removed HEAD entries with their counterparts' ids (B4) or the re-created commits' ids (B3), keeping time and
message, instead of removing them, and run the test again.

**B8 One notice, one log line, exit 0.** At most one line per Stop through P7b's notice channel (combined with any
other landing notice): what the re-sync did (counts: branches moved, local-only commits re-created, snapshots
re-created, stash entries, refs deleted, reflog entries removed, whether old objects remain in grace) or why it waits.
One append to the landing log with counts and revision ids; never a value. If the home has a private-literal list,
also log, once per re-sync, the number of its lines still found in the rewritten upstream history (blobs, paths and
messages; identities counted apart): the only check of the rewrite against the owner's real list, read on his machine
and reported as a count. Exit 0 always; a failure is a notice naming the step.

**B9 Bounded, idempotent, one at a time.** Under P7b's landing lock; each step idempotent, so a re-sync killed
half-way completes at the next trigger; the Stop's own share bounded (P7b's target: under 15 s; the auto_commit
phase's 120 s also holds the checkpoint). No network, no fetch, no pull, no push, no venv, no question.
