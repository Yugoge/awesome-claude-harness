**控制器自述这次错误的特殊之处，与本类别前三次不同**：前三次的推断源头是"看名称/看现象就下判断"，凭的是印象；**这一次两次判断都不是凭印象，而是给了字段级证据**——`created_at`、`updated_at` 都是真实存在、值也没读错的字段，不是猜测或转述。错的地方是：**用一个关于"文件"的时点字段，去回答一个关于"候选集合"的来源问题**。`prepare_state()` 写入的同一份 JSON 里，`created_at`/`updated_at` 描述的是状态文件这个对象的生命周期，`candidates` 数组里的每条记录才是候选这个对象；两个时间戳字段和这批候选，是同一份 JSON 里并列出现、但分属两个不同对象的信息，把前者的时间跨度当成后者的发现窗口，是对象错位，不是数值错误。

**教训（控制器原话，本台席原样收录，不改写）**："证据的硬度不保证相关性。一个真字段答错一个问题，比一个软证据答对更难被抓——因为核实'这个字段的值对不对'一律通过。"核验一个字段时，正确的问法是**"这个字段是关于哪个对象的"**，而不是**"这个字段的值准不准"**——后一问在这次错误里全程都会通过（`created_at`/`updated_at` 的值本身从未被读错），只有前一问才能拦下它。

**与类别 C 的关系（交叉引用，不并入）**：类别 C 记录的"真陈述贴错对象"（第九次、第十七次）是**陈述层面**的错配——一句为真的话被安在了错误的对象上；本实例是**字段层面**的同一形状——一个为真的字段值被用来回答关于另一个对象的问题。两者共享"内容为真、对象错位、常规核实测不出"这一根因，但粒度不同（一句话 vs. 一个字段），不合并为同一实例，仅作跨类别参照，供以后判断"这条新错误该归 C 还是归 E"时参考：若错的是"看名字/表层特征做的语义推断且未读定义"，归 E；若错的是"一句真话或一个真字段被安到了错误的指代对象上"，归 C。

**归入本类别（而非类别 C）的理由**：根因与前三个实例一致——语义信息（`created_at` 到底记录的是"文件创建时刻"还是"候选发现时刻"）就在 `prepare_state()` 的函数体里，未读代码、凭字段表面间隔做推断，是同一形状的第四次复发。

**本类别现有四个实例，均指向同一根因**：字段/函数的语义信息就在紧邻的定义或注释里，看名称或表层特征做推断比读一次定义更快，但错的时候代价是提出一条会造成回归的修法，而不只是一条记录不准。

### 类别 G：同一个事实，对内标了不确定性，对外没标

- **[✓ 可核实] 第二十三次**：把一组统计数字（状态/方向/层次/家族四组计数）连同"别采信，我没逐条复核"这条限定语交给台席，但转发给终端用户时只带了数字、没带限定语——同一份未经复核的数据，对台席标了不确定性，对会把它当结论引用的用户没标；控制器发现后补发了限定语给用户。本条依据控制器自述，本台席无法独立核实控制器与用户之间的对话内容。
