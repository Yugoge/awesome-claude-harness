## 一、三种 claim 核实的锚点，方法互不相同

核实一条 backlog 条目的 claim（尤其"某修法是否已生效"）时，先判断这条 claim 属于哪一类，再决定去哪里查、用什么命令：

| 类型 | 问的问题 | 正确核实方法 | 失效方式 |
|---|---|---|---|
| **部署断言** | 这段代码/这道校验当前是否真的在运行 | 查 **HEAD**：`git show HEAD:<file>` 或 `git cat-file -p HEAD:<file>`；不用 `grep`/`open()` 直接读工作树文件 | 只查活树会把"写好但未落库"误判为"已生效"——今晚 `#119`/`#123`/`#116` 三个独立实例证实 |
| **工件内容断言** | 这份历史文件本身记录了什么内容 | 直接读磁盘字节（`open()`/`Read` 工具即可） | 不因文件是否被 git 跟踪而改变其内容事实，与"是否已部署"是两个不同问题，不能用 HEAD-only 规矩去套 |
| **外部系统断言** | 本仓库之外的依赖（如 `/opt/paseo/node_modules/...`）当前行为是否还这样 | 直接读该外部路径当前磁盘内容，没有 git HEAD 可查 | **没有任何版本锚点**——外部依赖升级会悄悄改变行为，且没有 `git log` 能告诉你它变过，比坐标漂移更彻底：坐标漂了至少能重新 `grep` 定位，外部依赖换版本后连"原来是什么样"都查不到。核实时须注明核实当时的外部版本号（如可得）或安装目录 mtime；两者都拿不到时，至少注明核实日期作为可对照的时间点 |

**HEAD-only 规矩的适用范围必须明确写出，否则会被误读成"凡读文件都要走 HEAD"**——它只管"部署断言"，不管"工件内容断言"；今晚核实大量 `docs/dev/dev-report-*.json` 等历史工件内容时都是直接读磁盘，这些读取不受 HEAD-only 规矩约束，不需要回溯用 HEAD 重查。

### 一之二、同一锚点内部，字段可能分属不同对象——锚点粒度问题，不是第四种类型

上表区分的是三种不同的**锚点类型**（HEAD / 磁盘 / 外部系统）该用哪种方法核实；这一节讨论的是**同一个锚点内部**——比如同一份 JSON 工件的同一次磁盘读取——不同字段可能分属完全不同的对象，核实前必须先确认"这个字段归属哪个对象"，不能只确认"这个字段的值准不准"。这是锚点类型问题下面**一层**的锚点粒度问题，是第一节的子节，不是与三种类型并列的第四种。

实例（`hooks/lib/subagent_restart.py` 的 `prepare_state()` 写出的 `~/.claude/restart-state/<会话id>.json`）：

| 字段 | 归属对象 | 依据 |
|---|---|---|
| `created_at` | 状态文件本身 | `:572`，若旧文件存在则沿用其原值，不随本次运行改变 |
| `updated_at` | 本次 `prepare` 运行 | 每次调用都刷新为当前时间 |
| `candidates` | 本次 `prepare` 发现的候选集合 | `:543` 只遍历本轮 `discovered`、`:574` 全量替换——未被本轮重新发现的旧候选不留存 |
| 逐候选 `status`/`attempts`/`last_dispatched_at`/`last_stop_at` | 单个候选跨运行的历史 | `:552-565`，按 `agent_id` 从旧状态合并继承 |

这四个字段躺在同一份 JSON 的同一层级，却分属三个不同的对象：**文件本身**（`created_at`）、**本次运行**（`updated_at`、`candidates` 的取值范围）、**单个候选的跨运行历史**（`status` 等字段）。核实 `harness-issues-backlog.md#146` 时，曾取 `created_at` 去回答"这批候选是什么时候被发现的"——值是真的、字段是真的、可复现，但它回答的是"文件何时创建"，不是"候选集何时产生"，二者在这份 JSON 里恰好是不同的问题。

**核验问法的推论**：遇到一份多字段工件时，先问"这个字段是关于哪个对象的"，再问"这个字段的值准不准"——后一问在这次错误里全程都会通过（两个字段的值从未被读错），只有前一问能拦下它。这与本文件其余各节共享的原则一致：核实的第一步永远是确认问的是哪个问题、查的是哪个对象，其次才是取值本身是否正确。

**与 taxonomy 的关系**：`docs/reference/controller-error-taxonomy-20260924.md` 类别 E 第四实例记录的是这次具体错误的经过与教训（"证据的硬度不保证相关性"）；本节只固化其中可复用的核验方法本身，不重复该记录的具体过程。

## 二、坐标类引用（行号）的漂移判据

- **改动量大小不能用作漂移风险的代理指标**：同一批文件里，改动量最大的文件（如 `scripts/resolve-commit-repos.py` 某次 +145 行）坐标可能全漂，改动量次大甚至更大的文件（如 `commands/commit.md` +132 行）坐标可能完全不漂——决定因素是**插入点相对被引用行的位置**，与改动总量无关。
- **`git status` 为 `M` 不是判断是否需要重新核实的可靠依据**：一个文件当前干净（`git status --porcelain` 为空，工作树等于 HEAD）不代表它的坐标从未漂移过——只要条目记录之后、当前查验之前，有任何提交落库到该文件，坐标都可能已经过期，即便现在看起来"干净"。
- **唯一可靠的核实方式**：用条目文中给出的定位字符串（函数名、唯一字面量等）重新 `grep` 定位，不能直接信任行号本身，也不能靠"文件是否为 `M`"来判断要不要重新核实——坐标一律不可信，这一点没有例外。

## 三、claim 判定的第二条固定判据：I4 的状态判定形态

**"具体事件被人工解决"不等于"系统性缺口被消灭"。** 状态判定必须以"是否存在自动化机制（hook/gate/schema/gitignore/CLI-validation，即 I4 列举的合法修复形态）"为准，不以"某次具体事件是否已被人工处理过"为准——人工核实通过一次，不满足 I4 任何一条，条目状态不能因此从 OPEN 转为 FIXED。

未编号区大量条目正文同时记录两件事：条目描述的通用缺口，以及条目内引用的某一次具体历史事件（该事件可能已经过人工核实/手工修复而"解决"）。这两件事必须分开判断，否则会把系统性缺口系统性地误判为已解决。

## 四、"claim 已修复"的四种假阳性形态

同一个观察——"新逻辑和旧逻辑同时存在于 HEAD"——可能指向完全相反的结论，取决于新旧之间的关系：

1. **查活树当 HEAD**：修复只在工作树，HEAD 上没有。核实时压根没查对版本。（实例：`#119`/`#123`/`#116`）
2. **人工解决当机制修复**：一次性人工处理不满足 I4 任何一条自动化形态。（实例：未编号区"dev 子代理用仓库外临时账本自证归属完好"一条）
3. **新增而非替换，且旧路径正是缺陷本身**：HEAD 上新增了结构化/正确的判定路径，但旧路径原样保留、以"或"逻辑并列，旧路径仍可触发，而旧路径正是条目报告的那个错误逻辑。（实例：未编号区 `pretool-bash-safety.sh` 按命令原文做子串匹配一条）
4. **新在上游、旧在下游（分层，不是并列）**：新逻辑先对原始输入做宽松提取/规整，旧逻辑作用在提取后的文本上——这种情况下"两段代码都在"但**已经是修复**，因为下游此时处理的是新逻辑规整过的输入，不是原始未处理输入。（实例：`hooks/lib/close-verdict.py` 的正则回退在上游做宽松提取，`startswith("CLOSE:")` 严格路径在下游）

**判据不是"旧路径还在不在"，是"旧路径是不是缺陷本身，以及新旧之间是并列关系还是分层关系"**：
- 新旧并列 + 旧路径是缺陷 → 未修复（形态 3）
- 新旧并列 + 旧路径是正确设计（不是缺陷） → 无碍，可能已修复（视具体情况）
- 新在上游、旧在下游（分层） → 已修复（形态 4）

同一个"两段代码都在"的表面观察，必须先分清新旧的关系形状，才能判断结论，不能只看代码是否共存就下结论。

## 五、消费端容错：与"声明无比对者"相反的正面形态

`#144` 记录的大多数缺陷是"生产端声明、消费端不读"——声明存在但没人比对。`hooks/lib/close-verdict.py` 的修复是相反方向的正面实例：**不依赖生产端遵守声明，让消费端自己容错**（正则回退接受带 markdown 前缀的裁决行格式，即便生产端的散文约定被忽略或删除，消费端仍能正确解析）。双重防御（散文层 + 代码层）比单纯散文约定更可靠，因为代码层不依赖任何人记得遵守规则。

## 六、阴性断言的记录规范

任何"某机制/某校验不存在"的断言，必须附上查找方法与作用域（查了哪些文件、用什么关键词/模式），不能只写结论。范例见 `#133` 的"声明文件集与实际提交文件集从不比对"核实（明确列出查了 5 个文件、用什么关键词、命中的内容为何不构成反例、以及"未覆盖仓库其余脚本"这条作用域限制）。

## 七、HEAD-only 规矩的盲区：未落库内容用检查点快照做锚点

**HEAD-only 规矩对未落库内容是盲的。** 若某条目整条内容在 HEAD 上都不存在（`git show HEAD:<path>` 取不到，因为条目本身尚未提交），HEAD 无法回答"这段字节有没有被改坏"——本条来源：核实 `#110` 方法论抽出的编辑过程本身时，`#110` 整条不在 HEAD 上，HEAD 这个锚点直接失效。**该情形下唯一可取回的锚点是自动检查点历史**（本仓库为 `refs/checkpoints/<branch>`，每一两分钟一个快照提交），可直接 `git show <snapshot_sha>:<path>` 取任意历史时刻的未落库内容，与当前工作树逐字比对，定位改动发生在哪一步。

**补：这条锚点的深度足以回答几个月前的问题，不只是取回"当前尚未落库"的内容**——`refs/checkpoints/fix-dev-fanout-gatekeeper-20260717` 本台席独立核实 ✓：`git rev-list --count` = **5050**（另一时点为 5046，两次测量相隔数十分钟，属自动快照持续累积，非误差），最早快照可回溯到 **2025-12-27**。深度足够意味着这条锚点不止能回答"未落库内容有没有被改坏"，还能回答"某个文件在几个月前的某个具体历史时刻长什么样"——只要那个时刻落在自动快照的采样间隔（一两分钟一次）之内。**首次实战用例**：核实 `harness-issues-backlog.md#143` 时，用检查点在 `2026-09-23T12:45`/`12:58`（`20260923-121345` 周期的基线时刻附近）取回 `hooks/tests/INDEX.md` 的内容，逐字比对确认与基线 blob `9eb6f420…` 相同——证明"把该文件记成 `baseline_dirty_snapshot`"这条路即使打开也是一条假记录（该文件在那个时刻本就不脏）。**这是本文件记录的第一次把检查点锚点用于判定一个历史时刻的文件状态，而不是单纯取回一份当前仍未落库的内容**——用法从"救回丢失的字节"扩展到"重建任意历史切片"，两者都依赖同一个锚点，但问的是不同的问题（参见"一"节的锚点类型区分：后者更接近"部署断言"在历史时刻上的变体，前者是"工件内容断言"）。

## 八、计数类核对的两层盲区

第一层：标记计数（`grep -c` 命中次数、`wc -c` 总字节数）只能测"标记在不在、总量对不对"，**测不出内容有没有被错误拼接或错位**。

第二层（比第一层更隐蔽）：**在同一次编辑里若同时发生一次删除和一次新增，只要删除量与新增量恰好让某个子串的出现次数不变，计数核对连"总量变了"都测不出来。** 实证：`如实记录排除结果` 这八个字，编辑前基线里出现 2 次（分处两个不相邻段落），一次编辑删掉了其中一次（随所在段落一并移除），同一次编辑又在另一处误增了一次同样的八字短语（试图"接上"下文时把边界重复写了一遍）——净出现次数编辑前后都是 2 次，`grep -c` 完全测不出这处相邻重复。**只有检查相邻/连续出现（同一短语紧挨着自己出现两次）才能抓到，孤立的计数核对不够。可执行推论：涉及"删除+新增"混合的编辑，核对方式必须包含对编辑发生位置附近文本的直接复读，不能只看统计数字；要测内容错位，必须有一个可取回的基线（见第七节），计数不能代替它。**

## 九、正面实例：生产侧 fail-closed 拦下整体重写

对一份已存在的文件发起 `Write`（整体替换，而非 `Edit` 原地修改）时，本仓库的 write-guard 钩子会 fail-closed 拒绝：整体重写要求把全部内容从记忆里逐字节重建，任何一处遗漏或记错**不会报错**——且按第八节的判据，这类遗漏很可能连字节数核对都测不出来（如果遗漏与误增恰好抵消净变化）。这道闸门与第八节互为因果：正因为字节数与计数测不出这类遗漏，这类操作只能在入口处挡掉，不能指望靠事后核对补救。与第五节 `close-verdict.py` 的**消费侧**容错正例相对，这是本文件记录的第一条**生产侧** fail-closed 正例：不靠事后勤勉核查，靠结构性地不允许高风险操作发生。
